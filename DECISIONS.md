# Журнал решений

## План
1. Разобрать требования: админ создаёт услуги и слоты, клиент бронирует по дате.
2. Схема БД: `Services`, `Slots`, `Reservations`; слот уникален по
   `(ServiceId, SlotStartTime)`, бронь — по `SlotId`.
3. Backend на ASP.NET Core (Minimal API) + миграции + минимальная обработка ошибок.
4. Frontend: React SPA, страницы админа и клиента.
5. Собрать всё в Docker Compose (MySQL + backend + frontend).
6. Проверить сценарии (в т.ч. часовые пояса), оформить README и этот журнал.

## Где помогал ИИ
- Базовая «болванка» фронтенда (скелет компонентов, роутинг, форма) — ИИ.
- Полировка кода: поиск мест правок, чистка, оформление.
- Полировка документации: README и этот журнал решений.

## Ключевые решения
1. **Всё время в UTC.** Хранить и передавать слоты в UTC, браузер показывает
   локальное. Проще и надёжнее, чем хранить локальное время или `DateTimeOffset`
   — не путается «прошло/будущее» и границы дня.
2. **`DateTimeKind=Utc` в строке подключения.** Сначала endpoint сам
   конвертировал время в UTC, а фронт уже слал UTC — выходил лишний сдвиг
   (слот «11:00» в Минске сохранялся как «08:00»). Убрал повторную конвертацию
   и задал `DateTimeKind=Utc`, чтобы MySqlConnector читал/писал UTC без сдвигов.
3. **Мягкое удаление + уникальные индексы.** Слоты/услуги удаляем флагом
   `IsDeleted`, а уникальность слота и брони держим на уровне БД — так два
   клиента не забронируют один слот (гонка ловится атомарно, `409`).

## Что проверил и что осталось
- Сборка backend и frontend проходит без ошибок; слот «11:00» (Минск) теперь
  сохраняется/отображается корректно.
- Написал тесты: юнит-тесты валидации (35) и интеграционный тест гонки
  бронирования (Testcontainers + настоящий MySQL, 2 параллельных запроса → 1
  успех, 1 `409`). Все проходят.
- Осталось: нет авторизации админа, нет пагинации, границы «дня» считаются по
  UTC (без выбора зоны).
